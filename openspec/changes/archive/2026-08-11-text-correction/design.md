## Context

Текущий поток: `handlers.py` → `analyzer.analyze_text()` → подсветка банвордов + статистика. LLM-заготовка `llm_yandex.py` существует, но синхронная, вызывается на импорте, использует неверный endpoint и не подключена к боту; зависимость `openai` отсутствует в `requirements.txt`. Банворды — сленг («нейронка», «мастхев»), который pymorphy3 может не знать.

Мотивация и scope — в `proposal.md`. Поведенческие контракты — в `specs/`.

## Goals / Non-Goals

**Goals:**
- Ядро коррекции, пригодное для тг-бота и будущего веб-клиента (FastAPI).
- Гибрид: алгоритм правит явные опечатки и оформление бесплатно, LLM — грамматику/пунктуацию, получая уже подчищенный текст (меньше токенов).
- Затраты на LLM ограничены: переключатель, порог длины, кэш.

**Non-Goals:**
- Веб-клиент и FastAPI-эндпоинт — вне этой задачи (архитектура их учитывает, но не реализует).
- Показ списка правок «было → стало» (дифф) — не требуется, клиентам нужен финальный текст.
- Хранение состояния в БД — переключатель живёт в памяти процесса.

## Decisions

**1. Клиент-агностичное ядро + тонкие клиенты.**
Новый `app/analyzer/corrector.py` и существующий `analyzer.py` не импортируют ничего из Telegram. `handlers.py` только рендерит результат в сообщения. Будущий FastAPI обернёт то же ядро.
*Альтернатива:* логика прямо в хендлерах — отклонена: привяжет к Telegram и заблокирует переиспользование.

**2. Пайплайн из трёх стадий.**
```
исходник → [алгоритм: опечатки + оформление] → [LLM: грамматика/пунктуация] → [analyzer: подсветка банвордов]
```
Каждая стадия работает над результатом предыдущей. Подсветка всегда по финальному исправленному тексту — оффсеты пересчитываются заново, поэтому никакой возни со сдвигами.

**3. Алгоритмический этап (бесплатно).**
`razdel` токенизация → для каждого слово-токена: `pymorphy3.word_is_known`; неизвестные слова генерируют кандидатов по расстоянию Дамерау-Левенштейна ≤2, правка применяется **только при единственном кандидате**, иначе слово оставляется LLM. Не трогаются: банворды (белый список), числа, URL, эмодзи, имена собственные с заглавной буквы. Пунктуационно-оформительские правки регэкспами: пробел после `,.;:!?`, схлопывание двойных пробелов, заглавная после точки.

**4. Белый список банвордов — критично.**
`TARGET_WORDS` + `WORDS_LEMMA` загружаются в набор «не трогать». Иначе алгоритм начнёт «чинить» сленговые банворды в нормальные слова и сломает подсветку.

**5. LLM-клиент.**
`llm_yandex.py` переписывается в асинхронный класс (python-telegram-bot — async): `AsyncOpenAI`, промпт «вноси минимальные правки, не меняй слова и порядок слов, верни только исправленный текст». base_url и метод API (`responses` vs `chat/completions`) проверяются на реальном ключе до/в начале реализации — текущие значения в заготовке сомнительны.

**6. Переключатель `/correct`.**
Команда, состояние — `context.user_data["deep_correct"]`, дефолт — константа `DEFAULT_DEEP_CORRECT` в конфиге (в тесте `False`, в проде переключается на `True` одной строкой). Не переключатель = только алгоритм, LLM не зовётся.

**7. Порог длины и кэш.**
`DEEP_CORRECT_MAX_LENGTH = 1000`. Длиннее — только алгоритм + пометка. Кэш `{hash(text): result}` in-memory, без TTL в v1; повторная отправка идентичного текста (пользователи часто пересылают исправленную версию) не вызывает LLM. Потеря при рестарте допустима на этапе теста.

**8. Структура результата.**
`CorrectionResult` (dataclass): `original_text`, `corrected_text`, `algo_edits`, `deep`, `deep_note`. Статистика банвордов — отдельно, это результат `analyzer.analyze_text()`, как сегодня.

## Risks / Trade-offs

- [LLM «перепишет» слова/банворды, ломая подсветку] → Промпт жёстко требует минимальных правок и сохранения лексики; подсветка по финальному тексту, поэтому после имплементации проверить на тестовых примерах.
- [Грамматика недетектируема алгоритмом — «LLM по минимуму» сложнее, чем «не звать LLM»] → Экономия строится на кэше, пороге и переключателе, а не на триггере «алгоритм что-то нашёл». Принято осознанно.
- [Неверный endpoint/метод Yandex API в заготовке] → Спike в начале реализации: проверить рабочий вызов на реальном ключе, поправить base_url/метод и `max_output_tokens`.
- [Задержка LLM (2–5 сек)] → Уже есть сообщение «Анализирую текст...»; в режиме правки — «Исправляю...». Запрос асинхронный.
- [Затраты LLM] → Порог 1000 символов, кэш, переключатель off по умолчанию в тесте, капы не вводятся в v1.

## Migration Plan

1. Добавить `openai` в `requirements.txt`, поставить в `.venv`.
2. Новые константы в `config.py` (`DEEP_CORRECT_MAX_LENGTH`, `DEFAULT_DEEP_CORRECT`, настройки LLM).
3. Переписать `llm_yandex.py` (класс-клиент), написать `corrector.py`.
4. Подключить в `handlers.py`, зарегистрировать `/correct` в `bot.py`.
5. Ручной тест в Telegram с включённым переключателем; проверить банворды-сленг и их опечатки.
6. Откат: `/correct` off / откат коммита handlers — ядро остаётся, клиентская обвязка обратима.

## Open Questions

- Нужен ли TTL кэша и суточные капы на пользователя — решается после наблюдения за расходами в тесте, на спеки не влияет.
- Показывать ли на будущем вебе список правок (дифф) — вне scope, можно добавить позже отдельным изменением.
- Точные параметры Yandex API (модель, base_url, метод) — уточняются в спike, не меняют спеки и разбивку задач.
